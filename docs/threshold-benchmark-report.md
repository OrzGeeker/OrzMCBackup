## 1. 测试目标

1. 对同一真实世界，在 **6 档阈值（0 / 60 / 120 / 180 / 240 / 300 秒）**下各跑一次完整优化备份，
   对比**性能（耗时）与效果（体积、剔除区块数）**，其余参数一致（`--copy-misc --parallelism 4`）。
2. 对每档输出做**数据完整性验证**：不凭空新增区块/文件、非预期数据丢失为 0、entities/poi 与 region
   锁步一致、报告 `removedChunks` 与槽位推算交叉吻合。
3. 顺带验证 `merge` 槽位级合并（真实世界 + 真实优化备份 → 恢复结果）的完整性。

**性能结论**：
1. **耗时由输入读取主导**：6 档均需扫描全部 18.6GB / 3,162,906 区块，故耗时差异不大（15–27 分钟），

   不必为省时而压低阈值。

## 7. 附带发现：miscRel 经典布局缺陷与修复

真实世界验证过程中，在经典布局（根目录自身是维度 + 嵌套 `DIM-1`/`DIM1`）上发现 `miscRel` 的
排除逻辑缺陷：当某维度是另一维度的祖先（如根世界自身含 `region/`），祖先维度会错误地把嵌套维度
自己的杂项文件（`DIM-1/data/*.dat` 等）当成"他人子树"跳过，导致静默丢失。

- 修复：`if (excludePaths.any { !dir.startsWith(it) && p.startsWith(it) }) return null`
  （要求被排除项是当前源目录的**真后代/兄弟子树**，而非祖先）。
- 回归测试：`RealWorldPatternTest.classic layout nested dimension data files are preserved`
  （MemoryFS，验证 `DIM-1/data/{fortress_index,chunks,world_border}.dat` 与
  `DIM1/data/{endcity_index,raids_end}.dat` 保留）。
- **本测试世界为 26.1+ 嵌套布局（根非维度），不受此缺陷影响**——新旧逻辑在 3,162,906 区块上
  行为一致，本报告的阈值数据有效；修复后的 jar 已在真实世界复跑验证输出逐字节一致（见下）。

## 9. merge 合并验证

验证场景：`E:\recover\world`（08-12 全量备份，base）+ `E:\recover\world_backup`（08-15 优化备份，
patch）→ 新输出 `E:\recover\test_merge\world_recovered_test`（未覆盖既有 world_recovered）。

```powershell
& $java -jar backup.jar merge E:\recover\world E:\recover\world_backup `
  E:\recover\test_merge\world_recovered_test --parallelism 4 --progress-mode Off --report
```

**merge CLI 报告**（退出码 0）：

| 指标 | 数值 |
|------|------|
| `mergedRegions`（共享 region 数） | 1,244 |
| `patchSlots`（patch 提供的槽位） | 233,021 |
| `baseSlots`（base 填空的槽位） | 463,657 |
| `linkedEntities` / `linkedPoi`（锁步实体 / 兴趣点） | 98,384 / 10,022 |
| `overlayFiles`（杂项覆盖） | 7,353 |
| `errors` | **0** |

**独立槽位级复核**（`verify_merge.py` + `verify_lockstep_fast.py`，对 base/patch/output 三方逐槽比对）：

| 检查项 | 结果 |
|--------|------|
| 共享 region/entities/poi 检查 | 3,170（region 1,244 + entities/poi 1,926） |
| 共享 region 槽位并集（patch ∪ base） | 0 不一致 |
| 共享 entities/poi 锁步（源跟随 region 源） | **0 不一致** |
| 槽位 payload 逐字节来源核对 | **0 不一致** |
| 输出多余 .mca（base/patch 均无） | 0 |
| 仅 base 原样复制 | 18,275 个文件逐字节一致 |
| 仅 patch 原样复制 | 1 个文件逐字节一致 |
| 杂项覆盖（patch 优先 / base 补齐） | patch 6,760 / base 2 / 0 不一致 |

**关于 entities/poi 锁步语义**（重要，避免误判）：merge 按 `WorldMerger.mergeRegion` 设计，
每个槽的 entities/poi **源跟随同名 region 槽的源**——region 槽来自 patch 时，entities 只取 patch
entities（新状态无实体即无槽）；region 槽来自 base 时取 base entities。因此期望槽位是
`(patch_region ∩ patch_ent) ∪ ((base_region ∖ patch_region) ∩ base_ent)`，**而非**朴素的
`patch_ent ∪ base_ent`。首次以朴素并集期望复核时报 145 处"缺失"，逐槽排查证实全部是
"patch 保留了地形槽但 08-15 新状态已无实体"的正确丢弃（如 `entities/r.-1.-1.mca` 输出
entities=520 == patch 的 520，base 的 419 中仅 08-12 旧实体被正确让位）；修正验证逻辑后
**1,926 个共享 entities/poi 全部 0 不一致**，且输出无任何"有实体无地形"的孤儿槽。

**merge 结论**：18.64GB 全量 + 2.18GB 优化 → 恢复出"全量最新"地图（1,244 共享 region 的
696,678 槽位并集 + 18,275 个 base 独有文件），region / entities / poi / 杂项全部逐字节验证，
`errors=0`，与 [`papermc-map-backup-recovery-case.md`](papermc-map-backup-recovery-case.md)
既有结论一致。

## 10. 结论

1. **6 档阈值全部运行成功**（退出码 0、`errors=[]`、processedChunks=3,162,906 全量扫描），
   性能由输入读取主导（HDD 下 15–27 分钟），阈值不影响耗时。
2. **`-t 0` 已剔除 71.3% 区块**（18.6GB → 6.9GB，压缩 63.2%）；**60 秒即取得 91.3% 剔除率
   （相当于 t300 的 92.7% 的约 98%）**；更高的 120/180/240/300 秒边际收益递减。
3. **数据完整性逐字节验证通过**：6 档 0 新文件、0 槽位伪造、0 锁步违规、0 意外剔除，
   `removedChunks` 与实际 region 槽位差严格一致。
4. **本世界实际触发了部分重写路径**（t0 有 6,285 个重写 region），是对该路径最真实的覆盖测试。
5. **merge 恢复验证通过**：18.64GB 全量 + 2.18GB 优化 → "全量最新"地图；1,244 共享 region 槽位
   并集精确、entities/poi 与 region 源锁步 0 不一致、payload 逐字节 0 不一致、`errors=0`
   （详见第 9 节）。entities/poi 的期望槽位应遵循"源跟随 region 源"锁步语义，朴素并集期望会误报。
6. **运营建议**：默认 `-t 60~120` 秒（保留近期活跃区块 + 91–92% 压缩收益）；`-t 0` 适合激进归档
   （仅保留玩家真实访问过的区块）。更大世界（>10GB、HDD）建议保持 `--parallelism 4` 并开启
   `--copy-misc`，以 `--progress-mode Off` + `--report-file` 采集数据避免管道缓冲阻塞。
